# Общие соглашения (обе системы)

Документ обязателен к прочтению и бэкенду, и фронтенду: на него ссылаются все остальные файлы.

## 1. Что сделать в существующем коде до начала

Эти замечания найдены при разборе кода лидерборда. Без них новые модули выпускать нельзя.

**Бэкенд**

1. `authenticate_user` — заглушка (принимает любой логин и пароль). С ней модуль выпускать нельзя. Заменить по решению ПР1 ([../decisions.md](../decisions.md)): вход через корпоративный провайдер вуза или локальные учётные записи, сопоставление с витриной по корпоративной почте, приглашения для внешних экспертов и тренеров. Без реального входа не работают ни эксперты, ни тренеры, ни наставники расписания.
2. `complete_consent_flow` выдаёт группу `student` всем, кто дал согласие. Выдавать только при найденной записи в `students`; группу `expert` выдаёт назначение в аудиторию, `trainer` — назначение тренером.
3. `/api/auth/me/` должен возвращать список `roles`, например `["student","expert"]`; сейчас `get_role()` отдаёт одну роль.
4. `custom_exception_handler` подменяет `code` на HTTP-статус и не знает `LeaderboardException` (она не наследует `APIException`, отсюда 500). Доменные ошибки — наследники `APIException` со своим `default_code`; код брать из `exc.get_codes()`.
5. `DEFAULT_PERMISSION_CLASSES = AllowAny`: на всех новых эндпоинтах явно `IsAuthenticated` плюс проверка роли.
6. Файловое хранилище для материалов акселератора (S3-совместимое или `MEDIA_ROOT` с защищённой отдачей): сейчас его нет.
7. Новые Django-приложения: `events/` (общий модуль), `evaluations/` (оценки), `schedule/` (расписание). Импорты только в одну сторону: `schedule → evaluations → events`; общий модуль не импортирует оценки, оценки не импортируют расписание. Исключение: блок `evaluation` в `POST /api/events/` обрабатывает сервис оценок в той же транзакции.
8. Точки расширения (инверсия зависимостей), чтобы вышестоящий модуль мог влиять на нижестоящий без импорта: (а) в `evaluations` — реестр `OpenGuard`: приложение `schedule` при старте (`AppConfig.ready()`) регистрирует проверку «расписание опубликовано» и «у всех команд есть позиция»; её причины попадают в `event_not_ready`; (б) там же — реестр `OrderControl`: расписание сообщает, что порядок команд ведёт оно, и тогда `PUT /sections/{sid}/teams/` и Excel-импорт отвечают `schedule_controls_order`; (в) в `events` — реестр `AnnouncementEnricher`: расписание добавляет блок `my_schedule` в карточку анонса.
9. Журнал `audit_log` (решение ПР14) общий для всех модулей: `actor_id`, `action`, `entity_type`, `entity_id`, `event_id`, `before`, `after`, `created_at`; хранится не менее года.

**Фронтенд**

1. Пути в `src/api/config.ts` (`/api/login`, `/api/me`, `/api/leaderboard`) не совпадают с бэкендом (`/api/auth/login/`, `/api/auth/me/`). Привести к бэкенду; новые пути строить от констант `EVENTS_BASE = '/api/events'`, `EVAL_BASE = '/api/eval'`, `SCHEDULE_BASE = '/api/schedule'`.
2. Тип `AuthUser` не содержит ролей: добавить `roles: Role[]`.
3. При ответе 401 тихо обновить access-токен через `/api/auth/refresh/` и один раз повторить запрос: access живёт 30 минут, а защита идёт дольше.
4. Мобильной навигации нет: `Sidebar` скрыт на ширине меньше 1024 px (`hidden lg:flex`). Без неё экраны эксперта на телефоне не работают — отдельная задача.
5. Кнопки «сменить роль» нет: пункты меню появляются по ролям (A14).

## 2. Протокол API

- Базы: `/api/events/` (общий модуль, анонсы, акселератор), `/api/eval/` (оценки), `/api/schedule/` (расписание). Пути с завершающим `/`.
- Все эндпоинты требуют JWT (access 30 минут, refresh). Права: `IsOrganizer` (группа `organizer` или superuser), `IsExpertOfSection` (запись в `section_experts`), классы лежат в `common/permissions.py`; новые — `IsTrainerOfTrack`, `IsMentorOfTeam`.
- JSON, `snake_case`. Имена полей совпадают с колонками ERD. Даты ISO 8601, время дня `HH:MM`.
- Списки мероприятий, шаблонов, анонсов и поиск людей пагинируются: `?page=&page_size=` → `{count, next, previous, results}`. Команды мероприятия, аудитории, слоты отдаются целиком.
- Формат ошибки единый:

```json
{ "error": { "code": "event_not_ready", "message": "Нельзя открыть приём оценок: …", "details": { "reasons": [ { "code": "teams_without_section", "count": 2 } ] } } }
```

- Время: все проверки «до / после» — по серверному времени и часовому поясу вуза (Asia/Tomsk), не клиента. «Окончание мероприятия» — `event_date + end_time`.
- Защита от одновременной правки двумя организаторами: изменяемые ресурсы расписания (`event_schedules`, назначения) отдают `version`, запросы на изменение принимают `If-Match`, несовпадение — `409 stale_version`. Для существующих ресурсов мероприятий и оценок — желательно, не обязательно.

## 4. Принципы, общие для обеих систем

- **Тексты интерфейса** показываются дословно, как в этом пакете и в прототипе. Бэкенд возвращает `code` и `message`; фронт показывает `message` или свой текст по `code`.
- **Нет уведомлений, кроме карточек в ЛК.** Писем и страницы «Уведомления» нет (A19, A30). Карточки выводятся из состояния данных, отдельной сущности «уведомление» нет.
- **Итоги не публикуются студентам.**
- **Статусов выступления** («Ожидает», «Выступает», «Выступила») нет, автозакрытия приёма оценок нет.
- **Прототип** (`source/Прототип v5.dc.html` и др.) — источник интерфейса и текстов; в продукт не переносятся демо-панель, переключатель «Сегодня в прототипе», «Сеть», «Сбросить демо», данные в памяти вкладки, фиксированный список команд, один демо-файл Excel, жёстко прописанные аудитории 301/303/305.
