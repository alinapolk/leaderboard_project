# Принятые решения

Все вопросы, остававшиеся открытыми, закрыты решениями по принятой практике проектирования подобных систем (регистрация и расписание мероприятий, приём оценок, обработка персональных данных). Каждое решение внесено в файлы бэкенда и фронтенда; ссылки вида «ПР6» указывают на строки этой таблицы.

Решения принимались так, чтобы их можно было менять дёшево: большинство — конфигурация или одно правило в сервисном слое. Три решения (ПР1, ПР5, ПР6) зависят от фактов, которых нет в документах, — они выделены в конце.

## Решения

| № | Тема | Решение | Основание |
|---|---|---|---|
| ПР1 | Вход и роли | Перед релизом `authenticate_user` заменяется настоящей проверкой. Вход через корпоративный провайдер вуза (OIDC, SAML или LDAP — что есть у ТПУ); если провайдера нет — локальные учётные записи (argon2 или PBKDF2, ограничение числа попыток, блокировка). Студент и наставник сопоставляются с записью витрины по корпоративной почте; в `User` хранится идентификатор человека в витрине. Внешние эксперты и тренеры получают учётную запись по приглашению организатора (одноразовая ссылка на 7 дней). Группа `student` выдаётся только при найденной записи в витрине; `expert` и `trainer` — при назначении; роль `mentor` выводится из состава команды. Группа `manager` для прав в новых модулях не используется | Принцип наименьших привилегий; без реальной аутентификации выпуск невозможен. **Условие релиза, не вариант дизайна** |
| ПР2 | Лист защиты | При создании защиты шаблон предзащиты подставляется по умолчанию и может быть заменён, пока защита в черновике. Проходного балла у защиты нет (A22). При публикации шаблон блокируется | Защита оценивает проект по тому же листу, что предзащита, если организатор не решил иначе; порог нужен только там, где есть отбор |
| ПР3 | Команда без слота после публикации | Команда без слота и позиции не видна экспертам. Пока такая команда есть, приём оценок открыть нельзя: причина `teams_without_position` в `event_not_ready`. Если приём уже открыт, добавление команды разрешено; она не оценивается, пока организатор не поставит её в слот | Инвариант «оценивать можно только команду с позицией» проще и надёжнее, чем исключения |
| ПР4 | Порядок при открытом приёме | Внутри аудитории порядок можно менять в любой момент (у мероприятия с расписанием — сменой слота), оценки привязаны к участию команды, а не к позиции. Каждая правка пишется в журнал (ПР14). Между аудиториями после открытия приёма перенос запрещён (`move_after_open`): у аудиторий разные эксперты | Изменение порядка безопасно для данных, перенос между экспертными группами — нет |
| ПР5 | Причины отметок и 152-ФЗ | Причина обязательна, свободный текст 3–300 символов. Подсказка в форме: «Не указывайте медицинские и иные личные подробности — достаточно общей причины». Видят только организатор и автор. Текст причины очищается через 30 дней после даты мероприятия, интервал и статус сохраняются. Сбор и срок хранения указываются в тексте согласия. Список причин вместо текста — не в первой версии | Минимизация данных и ограничение срока хранения. **Правовую оценку должен подтвердить юрист вуза** |
| ПР6 | Лимит отметок | Формула без изменений (A34). Уже сохранённые отметки при смене сетки автоматически не удаляются: помечаются «превышен лимит» в разборе, новые отметки блокируются. При сохранении сетки показывается список затронутых команд. Если запас в аудитории меньше двух слотов, организатору показывается предупреждение «Запас меньше двух слотов: наставники почти не смогут отметить время». Отдельного потолка или множителя нет. Закреплённые команды и наставники с несколькими командами в формулу не входят: их учитывает решатель, а итог правит организатор | Лимит — защита от перегруженных отметок, а не гарантия выполнимости; потеря введённых данных хуже временного превышения. **Размер лимита утверждает заказчик** |
| ПР7 | Правило допуска | Организатор выбирает допущенные статусы; пока не выбраны, «Подтянуть команды» неактивна. Команды в статусе «Закрыт» (архив) не допускаются никогда. Начало и конец семестра вводятся вручную. Для каждой недопущенной команды показывается причина; организатор может добавить любую команду вручную. Правило — подсказка, а не запрет | Явная настройка вместо скрытых допущений; ручной обход обязателен для форс-мажора |
| ПР8 | Список записавшихся | Тренер видит ФИО и учебную группу записавшихся на свои направления; организатор — ещё и дату записи | Минимально необходимые данные |
| ПР9 | Удаление направления | Направление с записями удалить нельзя (`409 track_has_enrollments`). Лимит можно уменьшить ниже числа записанных | Защита от потери записей |
| ПР10 | Окно записи | Поле `registration_opens_at` необязательное. Эффективный статус считается на сервере по времени вуза: если дата открытия задана и наступила, запись открыта; организатор может открыть и закрыть вручную; в момент начала мероприятия (`event_date + start_time`) запись закрывается автоматически. Менять и отменять запись можно, пока она открыта (как в прототипе) | Типовая практика регистрации: открытие по расписанию, закрытие к началу, ручной выключатель |
| ПР11 | Эксперт удалён после оценки | Оценки остаются и учитываются в итоге. Удалить эксперта, отправившего оценки, можно только с `confirm: true` (иначе `409 expert_has_evaluations`). В «оценок N из M» удалённый эксперт входит в M | Нельзя терять результаты оценивания; удаление — осознанное действие |
| ПР12 | Вес критерия | Не вводится. Вес задаётся максимумом баллов | Проще и совпадает с прототипом |
| ПР13 | Окончание мероприятия | `event_date + end_time`, часовой пояс Asia/Tomsk | Единое правило для материалов и записи |
| ПР14 | Журнал изменений | Таблица `audit_log`: `actor_id`, `action`, `entity_type`, `entity_id`, `event_id`, `before` и `after` (json), `created_at`. Пишется при: публикации, смене статуса приёма оценок, неявке, смене и закреплении слота, решении по отметке, смене порядка, удалении эксперта или команды. Хранится не менее года. Прежнее время слота для пометки «Слот изменён организатором» берётся из журнала | Стандартная подотчётность для спорных результатов |
| ПР15 | Комментарий эксперта | Виден организатору и автору-эксперту; студентам и наставникам — нет | Минимизация доступа |
| ПР16 | Создание и удаление расписания | Создать можно у предзащиты и защиты, пока приём оценок не открыт. Удалить можно в `setup`, `collecting`, `draft` (с подтверждением, если есть отметки); после публикации нельзя. Порядок, заданный вручную или из Excel, при публикации расписания заменяется | Публикация — точка невозврата для участников |
| ПР17 | Решатель | OR-Tools CP-SAT, один рабочий поток и `random_seed = seed` для воспроизводимости, лимит времени 10 с (настройка `SCHEDULE_SOLVER_TIMEOUT`). Приоритеты целевой функции: 1) число поставленных команд, 2) число нарушенных отметок (принятая весит 2, на проверке 1), 3) случайный разброс от `seed`. Жёстко: один слот — одна команда, закреплённые, своя аудитория, наставник не в двух местах. До релиза — нагрузочный тест: 50 команд × 3 аудитории менее 5 с | Воспроизводимость и предсказуемое время — требования к любому планировщику |
| ПР18 | Хвосты прошлой фичи | A21 (команда с неявкой или без оценок не проходит), A23 (одна защита на предзащиту), A24 (ручное добавление не прошедшей команды с подтверждением и пометкой `manual`) принимаются как записано. Одна роль акселератора — одна аудитория. Презентации загружают только тренеры направления; материал виден только записанным на то же направление. Фильтры списка хранятся в параметрах адреса (можно переслать ссылку); добавляется фильтр `?year=` по году даты. Стиль кнопок — как в действующем фронте | Единообразие с существующим продуктом |
| ПР19 | Неявка и лимит | Команда с неявкой слота не занимает и в числе команд аудитории для лимита не учитывается | Следует из жёсткого правила публикации |
| ПР20 | Масштаб и сетки | Расчёт рассчитан на ≤ 200 команд и ≤ 6 аудиторий в мероприятии. Сетка задаётся отдельно для каждого мероприятия, у защиты своя | Запас над текущими 50 командами и 2–3 аудиториями |
| ПР21 | Смена сетки в черновике | Сохраняются назначения, чей слот остался (та же аудитория и время начала), остальные сбрасываются, включая закреплённые; перед сохранением показывается число сбрасываемых назначений и нужно подтверждение. Новые слоты сами не занимаются | Не терять ручную работу организатора без необходимости; прототип при этом пересобирает расписание сам, а главный документ сбрасывает все назначения — оба варианта хуже |
| ПР22 | Автоперестроение | Построение запускается только кнопкой «Построить» / «Перестроить» (и автоматически «fill» только после «Добавить слоты»). Прототипное автоперестроение после правок не переносится | Результат построения не должен меняться без действия человека |

## Что не решается дизайном и остаётся подтвердить заказчику

Эти пункты не блокируют разработку: реализованы значения по умолчанию из таблицы выше; после показа они меняются настройкой или правкой одного правила.

| Что | Почему не закрывается без заказчика |
|---|---|
| A26: команды время не выбирают | Вывод из слов PM, самим PM не подтверждён |
| A27: правило допуска и значения статусов команды | Значения статусов и признак «архив» в витрине не определены |
| A35: наставник не в двух местах одновременно | В требованиях не было |
| A41: запись на акселератор (лимит мест, смена выбора, окно) | Не обсуждалось с заказчиком |
| Размер лимита отметок (ПР6) | Формула временная |
| ПР1: корпоративный провайдер входа | Зависит от ИТ вуза |
| ПР5: правовая оценка хранения причин | Зависит от политики вуза в отношении 152-ФЗ |

Вопросы к заказчику и PM по текущему процессу (22 пункта) ведутся в главном документе, раздел «Открытые вопросы по расписанию».

## Не вошло в первую версию

- Редактирование и удаление опубликованного мероприятия (отмена, перенос даты).
- Письма и push (почта подключится в следующем году, A19).
- Публикация итогов студентам.
- Роли и права на уровне отделений (несколько организаторов).
- Экспорт итогов в Excel / PDF.
- Мобильные экраны организатора (заглушка).
- Антивирусная проверка файлов.
- Автоматическое распределение команд по аудиториям и учёт вместимости: фаза 2 после API расписания ТПУ (A29).
- Границы семестра из расписания ТПУ (A27).
- Запрос на изменение слота от студента: студент пишет организатору вне системы (A36).
- Список причин отметки вместо текста.
