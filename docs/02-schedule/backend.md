# Система 2. Расписание выступлений — бэкенд

Что делает система: на предзащите и защите команды время не выбирают. Организатор раскладывает команды по аудиториям и задаёт сетку, наставники отмечают, когда команда прийти не может, система строит черновик расписания, организатор разбирает и публикует его. Запись студентов на время выступления **не используется** (A26); запись остаётся только у акселератора (система 1).

Расписание у мероприятия необязательно. Если организатор его не создавал, мероприятие работает как раньше (порядок вручную или из Excel). Если создал — порядок команд задаёт только оно (A39). Отдельного флага «использует расписание» нет: признак — наличие строки `event_schedules`.

Зависимость: расписание импортирует модуль оценок (читает команды и аудитории, пишет `section_id` и `position` через сервис оценок); оценки расписание не импортируют. Влияние расписания на оценки (приём оценок открывается только после публикации; порядок команд ведёт расписание) реализуется точками расширения `OpenGuard` и `OrderControl`, которые расписание регистрирует при старте (см. [../00-common/conventions.md](../00-common/conventions.md), раздел 1, пункт 8). Общие соглашения и реестр кодов — [../00-common/conventions.md](../00-common/conventions.md). Модели мероприятий, команд и аудиторий — [../01-events-evaluation/backend.md](../01-events-evaluation/backend.md).

**Допущения (A26–A41).** Не подтверждены заказчиком: A26 (команды не выбирают время, расписание строит система), A27 (правило допуска), A35 (ограничение «наставник не в двух местах»), A41 (запись на акселератор). Решения Эгора, ещё не показанные заказчику: A29 (аудитории раскладывает организатор), A38 (защита по той же схеме). Реализованы значения по умолчанию из [../decisions.md](../decisions.md); они меняются настройкой после показа. Формула лимита (A34) временная, размер лимита утверждает заказчик.

## 1. Роли в процессе

| Роль | Что делает |
|---|---|
| Организатор | Создаёт расписание, правило допуска, сетку; раскладывает команды по аудиториям; открывает сбор; принимает и отклоняет отметки; строит, правит, публикует |
| Наставник (`mentor`) | Ставит отметки недоступности своих команд, пока открыт сбор; видит свой слот после публикации |
| Студент (член команды) | Видит слот после публикации |

Наставник — человек с ролью «Наставник» в составе команды из витрины (A28); права проверяются по составу из витрины, а не по группе Django. Связь с группой `manager` не выяснена. Вход наставника обеспечивается решением ПР1 (корпоративный вход или локальная учётная запись, сопоставление с витриной по корпоративной почте); это условие релиза расписания.

## 2. Модель данных

```
events 1─0..1 event_schedules 1─* event_slots *─1 event_sections
event_sections 1─0..1 section_grids
event_slots 1─0..1 slot_assignments *─1 event_teams
event_teams 1─* slot_unavailability
event_schedules 1─* schedule_runs
events 1─0..1 event_admission                    (правило допуска, A27, только предзащита)
```

| Таблица | Поля и правила |
|---|---|
| `event_schedules` | `event_id` (unique); `status`: `setup` / `collecting` / `draft` / `published`; `slot_minutes` (длительность выступления, > 0); `changeover_minutes` (смена команд, ≥ 0); `marks_closes_at` (дедлайн сбора отметок); `seed`; `built_at`, `published_at`; `created_by` |
| `section_grids` | `section_id` (unique); `break_start`, `break_minutes` — оба или ни одного; кофебрейк внутри времени мероприятия; у каждой аудитории свой (A31) |
| `event_slots` | `section_id`, `starts_at`, `ends_at`; уникальны (`section_id`, `starts_at`); создаются генерацией, пересоздаются при изменении сетки |
| `slot_assignments` | `slot_id` и `event_team_id`, **оба уникальны**; `is_pinned`; `assigned_by` (null — алгоритм); `run_id` (null — ручная постановка); `assigned_at`, `changed_at` |
| `slot_unavailability` | `event_team_id`, `starts_at`, `ends_at`, `reason` (обязательно), `review_status` (`pending` / `accepted` / `rejected`), `reviewed_by`, `reviewed_at`, `marked_by`, `created_at`; начало раньше конца, интервал внутри времени мероприятия |
| `schedule_runs` | `schedule_id`, `seed`, `started_by`, `built_at`, `result` (`complete` / `partial`), `issues` (json), входной хэш (команды, сетка, отметки): история построений, из неё берутся объяснения организатору |
| `event_admission` | `event_id` (unique), `statuses` (допущенные статусы команды), `semester_start`, `semester_end` (вводятся вручную до интеграции с расписанием ТПУ); у защиты не применяется |

Изменения существующих таблиц: `event_sections.capacity` (необязательное справочное, A29); `event_teams.order_source` получает значение `auto` вместо `booking` (A40).
День начинается в `start_time` и заканчивается в `end_time` мероприятия, в расписании это не дублируется. Отметка действует на **все** аудитории (A32). Колонки `from`/`to` не использовать: зарезервированные слова SQL.
Лимит отметок в таблице не хранится: он зависит от аудитории и вычисляется (раздел 5); API отдаёт его в поле `limits[]` по аудиториям и в карточке команды для наставника. Прежнее время слота после публикации (для пометки «Слот изменён организатором») берётся из `audit_log` (ПР14).

Правила, которых схема не гарантирует и которые проверяет сервисный слой: слот принадлежит аудитории команды (`slot_not_in_section`); слот занимает одна команда, команда — один слот (`slot_occupied`); отметка внутри времени мероприятия, начало раньше конца (`invalid_interval`); сетка не меняется после публикации (`grid_locked`); открыть сбор можно, когда все команды в аудиториях и слотов не меньше команд (`teams_without_section`, `not_enough_slots`); опубликовать — когда у всех команд без неявки есть слот (`schedule_incomplete`).

## 3. Статусы и переходы

| Код | Бейдж | Шаг мастера |
|---|---|---|
| (нет строки) | — | — |
| `setup` | Расписание не настроено | 1 «Команды и аудитории», 2 «Сетка» |
| `collecting` | Сбор отметок до {дата} / Дедлайн прошёл | 3 «Сбор отметок» |
| `draft` | Расписание построено, не опубликовано | 4 «Разбор» |
| `published` | Расписание опубликовано | 5 «Публикация» |

```
(нет) ──create──▶ setup ──open_collect──▶ collecting ──build──▶ draft ──publish──▶ published
                                                                  ▲  │                 │
                                                                  └──┘ перестроить,    └─ ручные правки слотов
                                                                       ручные правки     (статус не меняется)
```

| Переход | Кто | Условие |
|---|---|---|
| нет → `setup` | организатор | тип мероприятия `predefense` или `defense`, приём оценок не открыт (ПР16); задаются длительность выступления, смена, дедлайн (лимит считает система) |
| `setup` / `collecting` / `draft` → нет (удаление) | организатор | с подтверждением, если есть отметки; в `published` удалять нельзя (ПР16). Позиции в `event_teams` пишутся только при публикации, поэтому чистить нечего |
| `setup` → `collecting` («Открыть сбор отметок») | организатор | мероприятие опубликовано (`event_not_published`); слоты сгенерированы; каждая команда без неявки стоит в аудитории (`teams_without_section`); в каждой аудитории слотов не меньше команд (`not_enough_slots`); задан дедлайн. Наставникам выводятся карточки в ЛК (A30) |
| `collecting` → `draft` («Построить») | организатор | можно и до дедлайна, система предупреждает; сбор закрывается |
| `draft` → `draft` («Перестроить», ручные правки) | организатор | закреплённые команды не двигаются; новый seed по желанию |
| `draft` → `published` («Опубликовать») | организатор | у всех команд без неявки есть слот (`schedule_incomplete`). В одной транзакции записываются `section_id` и `position` в `event_teams`; студентам и наставникам выводятся слоты |
| `published` → `published` (ручные правки) | организатор | команда закрепляется, обновляется `changed_at`, позиции пересчитываются; сетку менять нельзя (`grid_locked`) |

Сетку (параметры и кофебрейки) меняют в `setup`, `collecting`, `draft`. Если сетка меняется в `draft`, сохраняются те назначения, чей слот остался (та же аудитория и то же время начала), остальные сбрасываются, включая закреплённые; перед сохранением система показывает, сколько назначений будет сброшено, и требует подтверждения (ПР21). Новые слоты автоматически не занимаются: организатор нажимает «Перестроить» (ПР22).

**Отметка** (`review_status`): `pending → accepted` / `rejected`, обратно возможно. Меняется, пока расписание в `collecting` или `draft`. Отклонённая отметка не учитывается в построении и лимите; в `draft` после отклонения нужно «Перестроить».

**Защита.** Те же шаги, но команды сначала переносятся из предзащиты без аудиторий (A38), правило допуска не применяется, организатор раскладывает команды по аудиториям сам.

**Позиция команды.** `position` — порядковый номер среди **занятых** слотов аудитории; пустые слоты номеров не занимают. Порядок, заданный до расписания вручную или из Excel, при публикации заменяется (ПР16). Единственный писатель `event_teams.section_id` и `position` у мероприятия с расписанием — сервис расписания, при публикации и при каждой правке после неё, в одной транзакции (A39); `order_source` ручной правки становится `manual`. Приём оценок открывается только после публикации расписания (A40).

## 4. Генерация слотов

Время — в минутах от полуночи. Обозначения: `dur = slot_minutes`, `gap = changeover_minutes`, кофебрейк `[break_start, break_end)`, `break_end = break_start + break_minutes`; если кофебрейка нет, проверка пересечения пропускается.

```
slots(section):
  t = day_start
  while t + dur <= day_end:
    if has_break and t < break_end and t + dur > break_start:   # слот пересекает кофебрейк
      t = break_end; continue
    yield t
    t += dur + gap
```

Пример: 10:00–17:00, выступление 15, смена 5, кофебрейк 12:30–13:00. До кофебрейка слоты 10:00 … 12:00 (семь; слот 12:20–12:35 заходит на кофебрейк и отбрасывается), после — 13:00 … 16:40 (двенадцать). Всего **19**. Без кофебрейка: 21 слот (10:00, 10:20, … 16:40). Масштаб: около 50 команд и 2–3 аудитории (со слов Эгора, подтвердить цифрами прошлых мероприятий).

## 5. Лимит отметок

```
step    = dur + gap
L(team) = max(0, |slots(section)| − |teams(section)|) × step          # минут на команду
U(team) = |{ s ∈ slots(section(team)) : ∃ отметка m (review_status ≠ rejected):
              m.starts_at < s + dur  и  m.ends_at > s }| × step
```

- Лимит одинаков для всех команд аудитории и не зависит от чужих отметок, поэтому очерёдность подачи не влияет (A33). При 19 слотах и 17 командах это 2 × 20 = 40 минут.
- Отметка «съедает» каждый слот, с которым пересекается; отметка в промежутке смены или кофебрейка слотов не занимает.
- Отметка отклоняется, если `U + step > L` (клик по слоту) или `U(новое состояние) > L` (интервал): «Можно отметить не больше {L} минут. Осталось {L−U}» (`mark_limit_exceeded`, `details: {limit, used}`).
- `L = 0` — отмечать нельзя: «В ауд. {X} слотов столько же, сколько команд, поэтому отметить время нельзя.»
- Лимит пересчитывается при изменении сетки и состава команд. Сохранённые отметки при этом не удаляются и не меняются: те, что превысили новый лимит, помечаются «превышен лимит» для организатора, новые отметки команды блокируются (ПР6). При сохранении сетки возвращается список затронутых команд. Если запас в аудитории меньше двух слотов, организатору показывается предупреждение «Запас меньше двух слотов: наставники почти не смогут отметить время».
- Формула временная. **Не учтено:** закреплённые команды, наставник с несколькими командами, пересекающиеся между собой отметки. Лимит не гарантирует выполнимость расписания: ответственность за итог у организатора (A33).

## 6. Построение (`build`)

| Часть | Содержание (A35) |
|---|---|
| Вход | команды мероприятия без неявки, их аудитории, слоты, отметки `pending` и `accepted`, закреплённые назначения, `seed` |
| Жёсткие ограничения | один слот — одна команда; закреплённые команды остаются на месте; команда занимает слот только своей аудитории; у одного наставника два выступления не пересекаются по времени **в любых аудиториях** |
| Мягкое условие | слот команды не пересекается с её отметками; если так не складывается, нарушается минимальное число отметок; среди равных вариантов выбор случаен и определяется `seed` |
| Выход | назначения; причина для каждой не поставленной команды и каждой нарушенной отметки; запись в `schedule_runs` |
| Объяснения | `all_slots_blocked` — команда отметила все слоты своей аудитории; `slot_shortage` — N команд могут выступать только в интервале, где всего M слотов (пример: «пяти командам подходят только слоты 12:30–13:30, а их там 3»); `mentor_overlap` — наставник стоит в двух аудиториях одновременно |

Реализация — OR-Tools CP-SAT (ПР17): один рабочий поток и `random_seed = seed` для воспроизводимости, лимит времени 10 с (настройка `SCHEDULE_SOLVER_TIMEOUT`). Приоритеты целевой функции по порядку: число поставленных команд; число нарушенных отметок (принятая весит 2, на проверке 1); случайный разброс от `seed`. До релиза — нагрузочный тест: 50 команд × 3 аудитории менее 5 с. Генератор случайных чисел — любой детерминированный с сохранённым `seed`; одинаковые входные данные и `seed` дают одинаковый результат. Режимы: `full` — с нуля (сохраняются только закреплённые); `fill` — «Перестроить»: сохраняются текущие назначения, достраиваются новые и освободившиеся. «Перестроить» запускается **только по кнопке** организатора; автоматически `fill` идёт лишь после «Добавить слоты» (ПР22). Прототип запускает `fill` автоматически после смены аудитории команды, добавления команд, смены кофебрейка, длительности и смены; в продукт это не переносится — результат построения не должен меняться без действия организатора. После публикации алгоритм сам ничего не пересчитывает (A36).

Построение синхронное, в транзакции с блокировкой строки `event_schedules` (`SELECT … FOR UPDATE`), с таймаутом; если решатель не уложился, возвращается лучшее найденное решение и `result = partial`. Сохранять `seed` и входной хэш для воспроизводимости.

**Слабые места эталонной реализации в прототипе** (`source/МодульРасписанияV5.dc.html`, функции `gen`, `build`): прототип строит жадно по аудиториям с паросочетанием (алгоритм Куна), день жёстко задан как 10:00–17:00. Не повторять: (1) отметки там жёсткие, команда остаётся без слота, а по A35 они мягкие; (2) список занятых слотов наставников заполняется по мере обхода аудиторий, поэтому закреплённые и сохранённые назначения в ещё не обработанных аудиториях конфликт не создают, а должны — перед обходом его надо заполнить всеми закреплёнными (а в `fill` — всеми сохранёнными) назначениями; (3) жадность по аудиториям не даёт глобального оптимума. Заменять на «общий поток» нельзя: условие по наставнику связывает аудитории и выводит задачу из класса потоков. Нужен решатель ограничений.

## 7. Ручные правки (`draft` и `published`)

| Действие | Эффект |
|---|---|
| «Поставить сюда» | Слот свободен — перенос; занят — диалог обмена «Слот {t} занят командой «B». Она перейдёт в слот {t₂}, «A» — в {t}. Обе команды закрепятся.» (если A стояла в той же аудитории), иначе ««A» встанет в {t} и закрепится, а «B» попадёт в «Не поставлены»» |
| Обмен | Команды меняются местами и закрепляются: «Команды поменялись местами и закреплены» |
| «Закрепить» / «Снять закрепление» | `is_pinned` |
| «Добавить слоты в ауд. X» | Кофебрейк сдвигается: `break_start = min(s0 + need × step, break_end)`, где `s0` — первый слот, пересекающий кофебрейк; затем `fill`. Тост «Добавлено N слотов в ауд. X. Поставлено K из M» |
| «Сократите кофебрейк в ауд. X» | Возврат к шагу 2 с подсветкой |
| Отклонение отметки в `draft` | «Отметка отклонена. Нажмите «Перестроить», чтобы она перестала мешать» |

После публикации: смена слота закрепляет команду; тост организатору «Слот изменён. Команда и наставник видят новое время»; у студента и наставника — «Слот изменён организатором» и прежнее время. Перенос команды в другую аудиторию при открытом приёме оценок запрещён (`move_after_open`); порядок внутри аудитории при открытом приёме менять можно (ПР4), каждая правка пишется в `audit_log`.

## 8. Правила

| # | Правило | Код / текст |
|---|---|---|
| P1 | Начало и конец интервала обязательны; начало раньше конца; интервал внутри времени мероприятия | «Укажите начало интервала», «Укажите конец интервала»; `invalid_interval` |
| P2 | Причина обязательна, свободный текст 3–300 символов. Подсказка: «Не указывайте медицинские и иные личные подробности — достаточно общей причины». Текст очищается через 30 дней после даты мероприятия, интервал и статус остаются (ПР5) | «Укажите причину»; подсказка «Укажите причину и нажмите «Добавить»» |
| P3 | Жёсткий лимит минут на команду; сверх лимита сохранить нельзя | `mark_limit_exceeded` |
| P4 | Лимит 0 | см. раздел 5 |
| P5 | Отметки только в `collecting` до дедлайна и до «Построить» | `collect_closed`; «Дедлайн прошёл. Сбор отметок закрыт, расписание готовится.» |
| P6 | Сохранение явное | «Нажмите «Сохранить»», «Отметка удалена. Не забудьте сохранить» |
| P7 | Причину видят только организатор и наставник, поставивший отметку; другие наставники, студенты, эксперты — нет | — |
| P8 | Слот студент и наставник видят только после публикации | — |
| P9 | Нехватка слотов в аудитории | «В ауд. {X} не хватает N слотов: сократите кофебрейк или выступление» |
| P10 | Публикация — только когда у всех команд без неявки есть слот | `schedule_incomplete` |
| P11 | Сетка не меняется после публикации | `grid_locked` |
| P12 | Excel-импорт порядка и перетаскивание порядка у мероприятия с расписанием недоступны (A39) | `schedule_controls_order` |
| P13 | Создать расписание можно, пока приём оценок не открыт; удалить — в `setup`, `collecting`, `draft` (ПР16) | `event_not_draft` |

## 9. API — `/api/schedule/`

Пути без префикса `/api/` отсчитываются от `/api/schedule/events/{id}/`. Доступ — организатор, кроме отмеченных. Все эндпоинты ○ (новые); названия путей — предложение, структура и коды следуют допущениям.

| Метод | Путь | Описание |
|---|---|---|
| GET | `/` | Статус, параметры сетки, аудитории, слоты, назначения, лимиты отметок `limits[]` по аудиториям (`limit`, `slots`, `teams`), неразмещённые и нарушенные отметки с причинами, команды с превышением лимита. Наставнику — только свои команды и отметки; студенту и члену команды — свой слот, только в `published` |
| POST | `/` | Создать расписание (`setup`): `slot_minutes`, `changeover_minutes`, `marks_closes_at` |
| DELETE | `/` | Удалить расписание в `setup`, `collecting`, `draft`; при наличии отметок нужен `?confirm=true`; в `published` — `409` (ПР16) |
| PATCH | `/` | Параметры сетки; кофебрейки `sections: [{section_id, break_start, break_minutes}]`. Ответ: слоты по аудиториям, нехватка. В `draft` сбрасывает назначения (в предупреждении — сколько); в `published` — `grid_locked` |
| GET, PUT | `/api/eval/events/{id}/admission/` | Правило допуска (`statuses[]`, `semester_start`, `semester_end`); только предзащита. Пока статусы не выбраны, `teams/fill/` отвечает ошибкой валидации (ПР7); статус «Закрыт» не допускается никогда |
| GET | `/api/eval/events/{id}/teams/pool/` | Команды витрины отделения с флагом `fits` и причиной «не допущена» («Статус «Заморожен» не допущен», «Начала работу вне семестра») |
| POST | `/api/eval/events/{id}/teams/fill/` | Подтянуть подходящие команды (`order_source = auto`); ответ — добавленные |
| POST | `collect/` | `setup → collecting`; ошибки `event_not_published`, `teams_without_section`, `not_enough_slots` |
| GET | `unavailability/?event_team=` | Отметки; причина — организатору и автору |
| PUT | `teams/{et_id}/unavailability/` | **Наставник.** Полная замена своих отметок команды `[{starts_at, ends_at, reason}]`; `mark_limit_exceeded`, `collect_closed`, `not_mentor`, `invalid_interval` |
| POST | `unavailability/{id}/accept/`, `/reject/` | Пока `collecting` или `draft` |
| POST | `build/` | `{mode: full\|fill, seed?: int, new_seed?: bool}` → `draft`; назначения, неразмещённые, нарушенные отметки; запись в `schedule_runs` |
| PUT | `assignments/{et_id}/` | Ручная постановка `{slot_id, is_pinned}`; `slot_occupied {other}` (клиент предлагает обмен), `slot_not_in_section`; в `published` команда закрепляется, позиции пересчитываются |
| POST | `swap/` | `{a, b}` — обмен, обе закрепляются |
| POST | `sections/{sid}/add-slots/` | Сократить кофебрейк и добавить слоты; затем `fill` |
| POST | `publish/` | `draft → published`; `schedule_incomplete`. Записывает `section_id` и `position` в `event_teams` |
| GET | `export.xlsx` | Выгрузка |
| GET | `/api/schedule/my/` | **Наставник.** Мои команды и статус расписания (карточки в ЛК, A30) |
| GET | `/api/schedule/my/performances/` | **Студент, наставник.** «Мои выступления»: мероприятие, аудитория, время, номер, `changed_by_organizer`, прежнее время |

Карточка анонса (`GET /api/events/announcements/{id}/`) для члена команды содержит блок `my_schedule` после публикации расписания.

## 10. Пограничные случаи

| Случай | Требование |
|---|---|
| Наставник сохраняет отметки после дедлайна или после «Построить» | `409 collect_closed`; сравнение с серверным временем |
| Сетку изменили, лимит уменьшился, у команды отметок больше лимита | Отметки сохраняются, помечаются «превышен лимит»; новые отметки команды блокируются (ПР6) |
| Отметка пересекает кофебрейк | Учитываются только пересечения со слотами |
| Команду добавили после построения (форс-мажор) | В `draft` — в разборе «Команда появилась после построения. Нажмите «Перестроить» или поставьте вручную.»; в `published` — команда без слота и позиции, организатор ставит её вручную; пока у команды нет позиции, приём оценок открыть нельзя (`teams_without_position`), а если он уже открыт, команда не оценивается (ПР3) |
| Два организатора нажимают «Построить» | Блокировка строки `event_schedules`; второй получает актуальный результат |
| Наставник ведёт команды в разных аудиториях | Алгоритм не ставит их одновременно (A35) |
| Слотов стало меньше, чем команд | Сбор нельзя открыть (`not_enough_slots`); в разборе блок нехватки с действием «Добавить слоты» |
| Публикация с неразмещёнными командами | `409 schedule_incomplete` |
| Сетку меняют в `draft` / `published` | Назначения сбрасываются (с предупреждением) / `grid_locked` |
| Отметка о неявке у команды | До построения: команда не размещается и в `teams(section)` лимита не входит (ПР19). После публикации: назначенный слот остаётся занятым, команда показывается как «Не явилась», позиции не пересчитываются |
